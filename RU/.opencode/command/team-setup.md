# /team-setup — онбординг проекта

Агент: только team-lead. Аргументы: $ARGUMENTS (slug проекта или `--settings` для перенастройки только режимов).

## Стандартный режим

1. Slug проекта — из аргументов или вопросом заказчику через инструмент `question`.
2. Проверка повторного онбординга: если `team-workspace/<slug>/models.json` существует, показать его и спросить, оставить или перенастроить.
3. Список доступных моделей: выполнить `opencode models` через bash; при недоступности — известный список провайдеров.
4. Спросить через `question`: «Настраивать модели по тирам или индивидуально?» — варианты: «По тирам (рекомендуется)» / «Индивидуально (12 вопросов)».
5. Настройка моделей:

   **По тирам** — один вопрос на тир через `question`; роль можно переопределить позже правкой `models.json` (канонического источника):

   | Тир | Роли | Рекомендация | Профиль |
   |---|---|---|---|
   | A — флагман | team-lead, architect | старшая (flagship) из доступных | Сложное рассуждение: оркестрация, проектирование |
   | Dev — генерация кода | backend-dev, frontend-dev | старшая (flagship) из доступных | Генерация кода + executable feedback (build/тесты) |
   | B — средний | tester, analyst, code-reviewer, security | старшая из доступных; допустима лёгкая | Структурированный текст, автотесты; ревью и уязвимости по критериям приёмки |
   | C — small | scout, researcher, integrator, devops | лёгкая (small/fast) из доступных | Поиск, суммаризация, git/CI-механика; самые частые вызовы |

   **Индивидуально** — опрос по всем 12 ролям по одному вопросу через `question`: team-lead, analyst, architect, scout, researcher, backend-dev, frontend-dev, code-reviewer, security, tester, integrator, devops. Вопрос: «Модель для роли `<роль>`» с подсказкой — рекомендация по тиру роли из таблицы выше и его профиль.

   Предлагать только модели из списка доступных (`opencode models`; при недоступности — известный список провайдеров); конкретные имена в этой команде не заданы и не выдумываются — рекомендация всегда выбирается из фактического списка доступных.
6. Записать `model: <provider/model>` во фронтматтер каждого `.opencode/agent/<роль>.md` и в `team-workspace/<slug>/models.json` (канонический источник).
7. Спросить про режим прогресса (heartbeat): on (рекомендуется) / off.
8. Спросить про режим запуска субагентов: `auto` (рекомендуется) / `confirm` / `custom-flow`.
9. Спросить про учёт токенов: on (рекомендуется) / off.
10. Спросить про компакцию по контрольным точкам (`compact_policy`): `plugin` (рекомендуется — плагин team-compact компактит сессию автоматически после каждого шага пайплайна) / `prompt` (team-lead публикует строку `[COMPACT]`, заказчик компактит вручную ctrl+x c).
11. Спросить про автопродолжение после компакции (`after_compaction_auto`): on (рекомендуется — конвейер продолжает сам после компакции каждого шага; team-lead сначала перечитывает state.json) / off (team-lead после каждой компакции ждёт заказчика). Спрашивать только при `compact_policy` = `plugin`; при `prompt` записать `false` (ручная компакция не продолжает автоматически).
12. Создать `team-workspace/<slug>/` с директориями 00-requirements … 08-delivery и `tmp/`, `state.json` (схема — оркестрационная часть устава в `.opencode/agent/team-lead.md`, раздел state.json; settings заполнены из шагов 7–11) и `models.json`.
13. `git init` + первичный коммит, если репозитория нет.
14. Отчитаться заказчику: режим heartbeat; режим запуска; учёт токенов; политика компакции; автопродолжение; напоминание перезапустить opencode для применения моделей.
15. Принять ТЗ.

## Режим `--settings`

- Без опроса моделей. Без пересоздания workspace.
- Только вопросы режимов: heartbeat, launch_mode, tokens_log, compact_policy, after_compaction_auto.
- Обновить `state.json → settings`; удалить устаревшие поля `custom_flow` / `show_subagent_prompt`.
- `settings.regression_mode` здесь НЕ настраивается (team-lead спрашивает перед финальным тестированием).

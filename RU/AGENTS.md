# Чартер команды — Virtual Software Development Team (slim)

Полная спецификация: `agent-team-spec.md` (v2.9-hybrid). Это сокращённый чартер: только инварианты, обязательные для каждого агента в каждом вызове. Оркестрационная часть чартера (пайплайны, шлюзы качества, state.json, контракты-двойники, протокол обмена) живёт в `.opencode/agent/team-lead.md`. При конфликте: `agent-team-spec.md` > чартер > файл агента; файл агента может сужать права и правила, но не ослаблять их.

## 1. Назначение

Виртуальная команда полного цикла разработки ПО. Заказчик передаёт техническое задание (ТЗ) тимлиду; команда доводит работу до результата, принятого заказчиком. Агенты, команды и скиллы находятся в `.opencode/`. Промпты, артефакты и общение — на русском. Идентификаторы и комментарии в коде — на английском. Python/pytest — стек по умолчанию для greenfield, если ТЗ не указывает иное.

## 2. Роли

`team-lead` — primary, оркестратор, единственная точка контакта с заказчиком. Субагенты: `analyst`, `architect`, `scout`, `researcher`, `backend-dev`, `frontend-dev`, `code-reviewer`, `security`, `tester`, `integrator`, `devops`.

## 3. Правила взаимодействия

1. Заказчик общается только с `team-lead`.
2. Субагенты никогда не обращаются к заказчику напрямую.
3. Вопросы заказчику доставляет team-lead через инструмент `question`.
4. Team-lead делегирует через инструмент `task` (`subagent_type` = имя агента).
5. Прямые вызовы `субагент → субагент` запрещены.
6. Цикл `development → review → security → testing` маршрутизирует team-lead.
7. Субагент не изменяет артефакты и зоны ответственности других агентов.
8. Team-lead может отклонить ответ `DONE`, если отсутствуют или противоречивы self-review, исполняемая обратная связь (executable feedback), доказательства, Definition of Done или `structured_output`.

### Шлюз безопасности (security gate)

Задача, затрагивающая аутентификацию, авторизацию, пользовательские данные, секреты/учётные данные, платежи, загрузку файлов или запросы к БД, построенные из пользовательского ввода, после `code-reviewer` обязательно проходит через `security`. Вердикт `security` — `FAIL` с любой критической/высокой находкой блокирует дальнейшие шаги до исправления. Контракт-двойник с `"security_sensitive": true` назначает шлюз безопасности, даже если текст задачи сам по себе его бы не вызвал.

## 4. Матрица инструментов (least privilege)

Блок `tools:` во фронтматтере каждого `.opencode/agent/<роль>.md` — единственный источник истины; не дублируйте его в `opencode.json`. `question` и `team_checkpoint` принадлежат только `team-lead` и отключены у всех субагентов. `bash` ограничен ролью. Доступность инструментов проверяется во время выполнения и не хранится в `state.json`.

## 5. Типы запросов и пайплайны

→ Оркестрационная часть: `.opencode/agent/team-lead.md`, раздел «Типы запросов и пайплайны». Субагентам не требуется: состав и порядок этапов определяет team-lead и передаёт в брифе задачи.

## 6. Процесс и шлюзы качества фаз

→ Оркестрационная часть: `.opencode/agent/team-lead.md`, разделы «Процесс и шлюзы качества фаз» и «Контрольные точки шага и компакция сессии». Ролевые требования из шлюзов продублированы в файлах соответствующих агентов. Компакция сессии на контрольных точках шагов идёт по `settings.compact_policy` (`plugin` — автоматически через плагин team-compact, при `after_compaction_auto` конвейер продолжается сам; `prompt` — вручную заказчиком); отсутствие означает `plugin`.

## 7. Карты решений

→ Оркестрационная часть: `.opencode/agent/team-lead.md`, раздел «Карты решений». Только team-lead публикует карты решений.

## 8. Структура рабочего пространства

→ Оркестрационная часть: `.opencode/agent/team-lead.md`, раздел «Структура рабочего пространства». Субагенту достаточно путей из `INPUTS`/`OUTPUTS` его файла и брифа задачи.

## 9. Правила артефактов

1. Человекочитаемые артефакты — markdown. Машиночитаемый JSON-двойник контракта `T<N>.json` — единственный тип JSON-артефакта; служебные файлы (`state.json`, `models.json`, `tokens.log`, `compaction.log`, `.compact-pending.json`) артефактами не являются.
2. Новая итерация = новый файл `-v<N>`; предыдущие версии никогда не перезаписываются.
3. Каждый артефакт открывается шаблоном шапки:

```markdown
# <тип> v<N>

Project: <project-slug>
Author: <роль>
Date: <YYYY-MM-DD>
Iteration: <N>

Related to: <контракт / требования / сценарии / связанные отчёты>
Depends on: <входные артефакты, когда применимо>
Evidence: <команды, результаты тестов, когда применимо>
```

Поле `Related to` обязательно. `Depends on` и `Evidence` обязательны для артефактов планирования, разработки, ревью, интеграции и тестирования, когда применимо.

4. Каждый контракт состоит из двух файлов с одинаковым базовым именем: `T<N>.md` (нарратив) и `T<N>.json` (машиночитаемый двойник). Они создаются, ревьюятся и обновляются вместе; двойник никогда не встраивается в markdown. Имена файлов контракта используют ID задачи без `-v<N>`; при пересмотре контракта оба файла обновляются вместе.
5. Код проекта живёт вне `team-workspace`, кроме отчётов и автотестов, где явно определено.
6. Временные файлы и временные среды агенты создают только в `team-workspace/<slug>/tmp`; team-lead удаляет `tmp` после акцепта delivery.
7. После сдачи черновики и все предыдущие версии `-v<N>` удаляются; финальные версии остаются в `00–07`, итоги — в `08-delivery`.

## 10. state.json

→ Оркестрационная часть: `.opencode/agent/team-lead.md`, раздел «state.json». Схему ведёт и обновляет только team-lead; субагенты читают её по необходимости.

## 11. Файлы контракта: нарратив и JSON-двойник

Каждый контракт разработки состоит из двух файлов с одинаковым базовым именем: `T<N>.md` (нарратив) и `T<N>.json` (машиночитаемый двойник). Двойник — самостоятельный JSON-файл, он никогда не встраивается в markdown. Нарративный контракт — источник истины для смысла, двойник — для полей запуска; они не должны противоречить друг другу. Обязательные поля двойника: `task`, `inputs`, `outputs`, ≥1 `acceptance`, `touches`, `blocked_by`, `security_sensitive`. Задача с отсутствующим или невалидным двойником не запускается и возвращается автору с `STATUS: NEED_INPUT`. Критерии приёмки дословно цитируются в брифы ревьюера и тестировщика. → Полная схема и чек-лист валидации: `.opencode/agent/team-lead.md`, раздел «Файлы контракта: нарратив и JSON-двойник».

## 12. Исполняемая обратная связь (executable feedback)

→ Ролевая часть: формат и правила — в `.opencode/agent/backend-dev.md`, `.opencode/agent/frontend-dev.md` (раздел «Executable feedback»); приёмка и re-run команд — в `.opencode/agent/team-lead.md` и `.opencode/agent/code-reviewer.md`. `STATUS: DONE` разработчика разрешён, только если требуемые сборка и юнит-тесты проходят.

## 13. Правило передачи (handoff)

Каждая передача между агентами — артефакт со схемой: бриф задачи, ответ субагента, нарративный контракт, JSON-двойник контракта, отчёт разработчика, отчёт ревью, отчёт безопасности, отчёт тестирования. Пересказ в чате никогда не является валидной передачей. Если у обязательного входа нет пути артефакта, принимающий агент отвечает `STATUS: NEED_INPUT`.

## 14. Глобальные ограничения

- **Матрица инструментов**: least privilege обязателен; `tools:` во фронтматтере — единственный источник истина (§4).
- **Шлюз безопасности**: как в §3; отключение безопасности допускается только в custom-flow с явной зафиксированной акцептацией риска.
- **Языки**: промпты, артефакты, общение — на русском; идентификаторы и комментарии в коде — на английском; автотесты используют тестовый фреймворк проекта; Python/pytest — по умолчанию для greenfield.
- **Правила безопасности**: секреты только через переменные окружения и `.env.example`; без необходимости не передавать данные заказчика внешним сервисам; никогда не отправлять секреты, учётные данные, персональные данные или код заказчика во внешние MCP-серверы или на сайты; находки конкретные, действенные, с градацией серьёзности.
- **Внешняя информация и MCP**: сначала локальные источники; затем `context7` для документации библиотек/фреймворков/SDK/API, `fetch` для известных URL, `ddg-search` для поиска; `webfetch` — fallback только там, где разрешён `fetch`. Цитировать каждый источник (название, URL, дата обращения, тезис), фиксировать использованный инструмент и fallback, не выдумывать URL и версии, не обходить матрицу через `bash`/`curl`/`wget`. `security` и другие роли без внешних инструментов маршрутизируют вопросы через `researcher`. Доступность MCP-серверов проверяется во время выполнения и никогда не сохраняется в `state.json`.
- **Учёт токенов**: плагин team-tokens ведёт `tokens.log`; агенты его никогда не редактируют; статистику показывает `/team-tokens-used`.
- **Оркестрационные ограничения** (лимиты итераций, параллелизм ≤3, learnings, очистка, git-политика, heartbeat, протокол сбоя субагента, приоритет разрешения конфликтов): → `.opencode/agent/team-lead.md`, раздел «Глобальные ограничения (оркестрационные)».

## 15. Протокол обмена

### 15.1. Бриф задачи и уведомления о запусках

→ Оркестрационная часть: `.opencode/agent/team-lead.md`, разделы «Бриф задачи» и «Уведомления о запусках». Субагент получает бриф в вызове `task` и отвечает по REPLY CONTRACT из шапки своего файла.

### 15.2. Формат ответа субагента

→ Определён в REPLY CONTRACT шапки каждого файла агента; сводный формат — `.opencode/agent/team-lead.md`, раздел «Формат ответа субагента». `STATUS: DONE` требует `SELF_REVIEW: PASS`; `DONE` разработчика требует `EXECUTABLE_FEEDBACK: PASS` (или `WAIVED` с зафиксированным отклонением); при блокировке — `QUESTION` / `NEED_INPUT` / `FAIL`.

### 15.3. Блок structured_output

Каждый ответ субагента заканчивается огороженным YAML-блоком `structured_output`, содержащим всегда: `task`, `iteration`, `role`, `status`, `artifacts`, `created_modified`, `risks`, `open_questions`, `next_actions`, `learnings`; по ролям: ревьюер добавляет `verdict`, `counters`, `acceptance_summary`, `acceptance_details`; security добавляет `verdict`, `counters`, `security_required`; tester добавляет `verdict`, `scope`, `counters`, `acceptance_summary` при наличии двойников; разработчики добавляют `dod_satisfied`, `executable_feedback`; analyst/architect/scout/researcher/integrator/devops добавляют `dod_satisfied`, когда был предоставлен DoD. Используйте `null` для неприменимых полей, пустые массивы при отсутствии элементов, ничего не выдумывайте. Блок дополняет, а не заменяет человекочитаемый ответ и не должен ему противоречить. Отсутствующий или невалидный блок возвращается с `NEED_INPUT`.

### 15.4. Уведомления о запусках

→ Оркестрационная часть: `.opencode/agent/team-lead.md`, раздел «Уведомления о запусках» (дайджесты `[DISPATCH]` / `[RESULT]` / `[COMPACT]`).

### 15.5. Полнота тестирования

→ Ролевая часть: `.opencode/agent/tester.md` (колонки матрицы трассируемости, отчёт); решение об объёме регрессии — за team-lead.

### 15.6. Режим custom-flow

→ Оркестрационная часть: `.opencode/agent/team-lead.md`, раздел «Режим custom-flow». Для субагентов: отключённый этап в них не вызывается; остальное неизменно.

## 16. Приложение A — стандартный скелет роли

→ Скелет ROLE/MISSION/INPUTS/OUTPUTS/CONSTRAINTS/REPLY CONTRACT и ролевые промпт-блоки встроены в шапки файлов `.opencode/agent/<роль>.md`; эталон — `agent-team-spec.md`, Приложение A. Блоки можно сужать, нельзя ослаблять или удалять.
